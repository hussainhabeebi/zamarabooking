# Baggage selection readiness

TripJack Review already supplies per-segment BAGGAGE SSR options. Booking sends selections per passenger as key/code pairs; the server validates selections against the stored review, adds supplier prices to the authoritative total and persists SSR codes in booking tripjack.pax metadata. The queue forwards these codes as travellerInfo[].ssrBaggageInfos. No new provider parameters are added.

This patch makes unavailable ancillary baggage explicit per segment, shows the fare's included allowance without inventing an allowance per segment, displays selected baggage per traveller/segment before payment, clears stale baggage/meal choices when review sessions change, rejects malformed/missing/negative provider prices instead of making them free, and rejects duplicate SSR selections on a segment. Infants remain unsupported for ancillary baggage. Hold bookings still cannot add ancillaries.

Riya/Duffel/Akbar expose included baggage data in the current adapters but this flow does not have a verified optional-baggage booking path for them. No claim of provider-wide unsupported capability is made: their provider docs/entitlements and adapters need separate verification. Akbar PRs are not merged here.

The existing /checkout/[token] payment-link flow edits an already-priced booking. It has no ancillary re-review/reprice endpoint. Adding controls there without authoritative repricing could charge the wrong amount, so this patch does not enable baggage changes there. Customers must choose extra baggage during /book before the priced booking is saved. A separately reviewed pending-booking reprice/expiry/idempotency design is needed for payment-link ancillary edits.

Certification tests are explicitly sanitized LOCAL FIXTURES: one-way without/with additional baggage and round-trip without/with additional baggage, including two passengers and separate outbound/inbound keys. They verify SSR totals and outgoing supplier payloads with fetch mocked. These are not certification logs or evidence of supplier acceptance. Existing booking metadata retains selected codes, but actual supplier-returned ancillary details have not been verified. No live searches, bookings, payments, cancellations, migrations or deployments were executed.

Remaining certification gates: obtain a UAT fare whose review actually offers BAGGAGE options; confirm target supplier (TripJack vs Akbar); separately authorize four UAT booking scenarios; capture genuine review/book/status responses and confirm baggage for each traveller and segment in supplier booking details. Never infer acceptance from the local selection or payment status. No database schema or payment configuration change is required for this patch. Do not merge/deploy until approved.
